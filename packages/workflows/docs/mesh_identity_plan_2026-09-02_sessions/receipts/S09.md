## 1. `prop_mesh/sheet_render.py` — any GLB to a registrable 16-view sheet

Before this session the library could only ever hold ONE asset: the only renderer that
emits a registrable sheet is `pufferball_sheet.py`, which imports the Pufferball build
module and its look patches at the top of the file, and `hurlbat_sheet.py` renders three
angles with no passes at all. `sheet_render.py` has no subject-specific knowledge.

**CLI**

```
blender -b --factory-startup -P prop_mesh/sheet_render.py -- \
    --glb <file.glb> --out <build_dir> \
    [--name N] [--res 1024] [--samples 48] [--scale 1.0] [--max-parts 24] \
    [--views a,b,…] [--turntable N] [--drop-nodes _locks,_tuft] \
    [--no-ground] [--no-passes] [--manifest-only] [--allow-hidden-parts] [--cpu]
```

Emits, into `<build_dir>`: `beauty/<view>.png`, `passes/<view>_{depth,normal,index}_0001.exr`
(32-bit), `sheet.json`, and a copy of the source GLB. The 16 view ids / azimuths /
elevations / framings are byte-for-byte the Pufferball's, so `top_down` means the same
viewpoint on every asset in the library.

Deliberate choices, each because the alternative has already cost this repo a rebuild:

* **normal channels** go through `pass_lib.rgb_named_socket`. Wired straight through, the
  VECTOR socket writes X/Y/Z-named EXR channels, cv2 resolves one, and `passes_io`
  correctly calls the pass unusable — 16 EXRs shipped that way on 2026-08-26.
* **`cam_r` per view** (the camera's 3×3 world rotation), or the world-space Normal AOV
  cannot be taken to camera space and is not valid ControlNet input.
* **`ground` is index 1 on every sheet**, never taken by a mesh, because `mesh_control`'s
  default exclude is that NAME. A sheet without it hands the floor most of the depth
  range.
* **one render per view**, not two. The Pufferball renders data passes separately because
  its passes must be bald; a generic GLB has no fur, so the beauty PNG and the three EXRs
  come off the same trace.
* **the part vocabulary is sanitised, never invented.** `Group`, `Group_1` and bare UUIDs
  are what GLB node names actually are. Above `--max-parts` distinct nodes the vocabulary
  collapses to one `subject` index rather than shipping a 300-entry `idx` no exclude list
  could use.
* **visibility is a hard failure** (exit 3, unless `--allow-hidden-parts`): every part in
  the scene must own IndexOB pixels in at least one view. This is the check that would
  have caught the Pufferball's buried mouth on day one.
* **the GLB is copied, never re-exported.** A round trip through Blender's exporter would
  change the bytes the registry hashes, and the geometry must stay the pack's own for its
  CC0 provenance to mean anything.

## 2. `prop_mesh/sheet_register.py` — the driver, and the licence inheritance

`sheet_render.py` imports bpy, so it can only run inside `blender -b`; everything either
side of the render is ordinary Python that must NOT run in Blender's bundled interpreter
(no cv2 → `geom/passes_io` → the control build would skip itself and report success).

```
/usr/bin/python3.12 prop_mesh/sheet_register.py --glb <pack GLB> --id <asset_id> \
    --name "…" --description "…" --tags a,b --samples 48 --res 1024 --control \
    [--creature-id <cid>] [--replace] [--skip-render] [--dry-run] [--views …]
```

Two refusals, both measured rather than theorised:

* **no PROVENANCE.json → no registration.** An asset with a guessed licence is worse than
  no asset, because nothing downstream can tell them apart.
* **no trimesh in the interpreter → no registration.** `prop_mesh_library.register()`
  swallows `geometry_stats` and `export_mesh3d` failures into an `{'error': …}` field and
  still writes the record. Measured: run under the server venv (which has no trimesh) the
  record comes back with `size_m: null` and no `mesh3d.bin` — no 3D preview, no
  real-world size — and `verify()` still calls it ok. Caught the first workbench
  registration; re-run under `/usr/bin/python3.12` it lands complete.

**A defect found and fixed in the licence resolution.** The first version walked up to the
NEAREST ancestor with a PROVENANCE.json. `smithsonian/Mammals/` carries its own unit
provenance, so a cranium resolved against the unit, matched no registry row, and came
back with the pack's DEMO_KEY search URL as its `source_url` and no record id — a licence
that is still true attached to a provenance that points at nothing. It now tries every
ancestor and takes the one whose `registry.json` actually has a row for the file.
It also records the file's own sha256 separately from the pack row's, because a
Smithsonian row keys on the file (its sha256 IS the GLB's) and a Kenney row keys on the
pack (its sha256 is the zip's, and says nothing about this mesh).

## 4. View-rank receipt per asset (gate 3) — and it does NOT come out the same way twice

`prop_mesh/view_rank.py`. One klein render per arm per asset, seed 7, 24 steps, 1024².
`top_down`'s own control depth as reference image 1; the asset's `front_full` BEAUTY
render as reference image 2 — **deliberately the wrong view**, so the two conditioning
signals are in opposition. Using top_down's own beauty as the appearance reference would
have let an inert adapter score rank 1 by copying it. Rank of the true view among all 16
by DINOv2 CLS cosine (`creature_identity.similarity_emb`). Chance = 8.5.

Null = **adapter off**: same prompt, same front reference, no control image and no
RefControl LoRA (`klein_edit_angle`). Not "nothing" — everything except the geometry.

| asset | arm | rank(top_down) | cos(top_down) | rank(front_full) | top-1 | s |
|---|---|---|---|---|---|---|
| `kenney_workbench` | **ctrl** | **1** / 16 | 0.7170 | 6 | `top_down` | 77.9 |
| | null (adapter off) | 16 / 16 | 0.2473 | 7 | `close_q_left` | 53.7 |
| `si_gorilla_cranium` | ctrl | 12 / 16 | 0.3732 | **1** | `front_full` | 71.3 |
| | null (adapter off) | 13 / 16 | 0.2587 | **1** | `front_full` | 53.3 |

**Workbench: the depth wins outright.** Rank 16 → 1 of 16 against a chance of 8.5, and the
appearance reference's own view falls to 6 — the geometry beat the photograph it was
fighting. That is conditioning, not decoration.

**Cranium: no measured steer.** 13 → 12 is inside the noise of n=1, and `front_full` is
rank 1 in BOTH arms: the appearance reference won and the depth changed almost nothing.
Reporting the mean of these two assets as "the depth steers" would be the lie this
receipt exists to prevent.

**Why, measured rather than guessed:**

```
                    top_down control map    depth span    subject grey p5..p95
kenney_workbench    coverage 0.5333         94.4 mm       14 .. 234   std 64.1
si_gorilla_cranium  coverage 0.0915         318.4 mm      45 .. 236   std 58.6
```

The cranium's top-down control image is **91% background**. The camera solve frames on
the bounding box's LARGEST dimension, and the cranium is 0.169 × 0.140 m across but
0.326 m tall — so a view looking straight down the long axis fills a ninth of the frame
while the workbench (0.33 × 0.30 × 0.29 m, near-cubic) fills half of it. An adapter
handed a map that is nine-tenths empty has almost nothing to condition on. This is a
FRAMING defect in `sheet_render.place()`, not a defect in the adapter, and it is the
single most useful thing this measurement produced.

n=1 per arm per asset (the brief's budget). This is directional: it separates rank 1 from
rank 12, and it cannot separate rank 12 from rank 13 — which is exactly why the cranium
row is written as "no measured steer" rather than as a small win. The full 16-row cosine
table for every arm is in `output/view_rank/<asset>/view_rank_top_down_7.json`, so a
later run can pool seeds without re-rendering these.

One new generative op in `creature_fx.py`, applied as a single atomic write (patched in

```
          "params":[{"k":"v","lb":"Angle","t":"e","df":"front_full","opts":[…16 view ids…]}]}
```

**No page change was needed, and that is the design working.** `inspection.html` holds no
tool list — both bars are drawn from this endpoint, and `ctToolHtml` derives the `~` pip
(`.crst-tool.gen::before{content:'~'}`) and the `[generative: a diffusion edit, so it
needs a render before you can see it]` tooltip from `cls === 'edit'` alone. The op is
marked the same three ways as the other 133 because it is the same kind of record.

**What it does at render time.** `_run_edit` now looks for a live `cm_mesh` row, resolves
the creature's registered mesh through `prop_mesh_library`'s own `creature_id` field (not
a path convention), runs `mesh_control.ensure`, and passes the view's depth PNG to
`generate_still(pose_image=…)`. `comfy_generation_service`'s `qwen_edit_angle` branch
already injects that as `image2` on nodes 20/21 and already drops the angles LoRA to
`ZYG_QWEN_EDIT_ANGLES_LORA_SCALE_CONTROL` (0.0) when a control image is present — so the
brief's "angles LoRA forced to 0" needed no service change, only a caller that supplies
the map.

One line had to change beside the call: `wants_angle` is `any(c['op'].startswith('cm_'))`,
and `cm_mesh` starts with `cm_`, so the sidecar would have recorded `angles_lora: 1.0`
for a render the service ran at 0.0. It now reports the value actually used, and records
`mesh_view: {asset, depth}` — or `{unavailable: <reason>}`.

## 6. TRELLIS.2 texturing — the nvdiffrast verdict

**Does the texturing stage need nvdiffrast? Yes to import, no to run.** That distinction
is the whole finding.

```
trellis2/pipelines/trellis2_texturing.py:13   import nvdiffrast.torch as dr      # module scope
                                     :316     ctx  = dr.RasterizeCudaContext()
                                     :318     rast, _ = dr.rasterize(ctx, uvs, faces, resolution=[S,S])
                                     :323     pos  = dr.interpolate(vertices, rast, faces)[0][0]
/home/zygomatic/TRELLIS.2/venv        ModuleNotFoundError: No module named 'nvdiffrast'
```

The import is at module scope, so `Trellis2TexturingPipeline` cannot even be *imported*
on this build. But all three calls sit inside `postprocess_mesh`, in UV space, under
`@torch.no_grad`: rasterise the UV atlas, and for every texel recover the 3D surface
point it belongs to. No camera, no gradients — the one thing nvdiffrast is actually for
is unused here.

nvdiffrast is NVIDIA Source Code License (non-commercial) and is on this box's banned
list, so installing it "just to try" would put a non-commercial dependency in the render
path of a monetised pipeline. Instead: `/home/zygomatic/TRELLIS.2/ztest/nvdr_shim.py`,
~80 lines of torch implementing `rasterize` and `interpolate` to nvdiffrast's own
conventions (`rast = [bary_u, bary_v, z, tri_id+1]`, `attr = u·A₀ + v·A₁ + (1−u−v)·A₂`,
row 0 = the BOTTOM of the image). Triangles are sorted by pixel-bbox size and rasterised
in chunks over a local k×k window, so a 2048² atlas costs tens of millions of point tests
rather than F·S².

It carries its own self-test, because a rasteriser is exactly the kind of code that looks
right and is off by a row:

```
./venv/bin/python ztest/nvdr_shim.py
nvdr_shim selftest OK on cuda (36 texels covered)
```

`install()` **refuses to run if nvdiffrast is ever actually present** — a shim that could
shadow a real installation would hide the licence question rather than answer it.

Licence entries for all of this are in `data/runtime/model_licences_pending/S09.json`
(3 entries: TRELLIS.2-4B texturing weights MIT — read at file level in both
`/home/zygomatic/TRELLIS.2/LICENSE` and the downloaded snapshot card, not from a badge;
an explicit **DENY** for nvdiffrast; and the CC0 source geometry of the two new assets).
Nothing was downloaded this session — the 16 GB TRELLIS.2-4B snapshot was already on disk
and had simply never been registered.

### Looking at it (`output/texturing/texturing_side_by_side.png`)

The number is small and the picture says why. The texture IS broadly right — cream/mint
body, green limbs, a green-and-white striped tail, a pink nose, blue eyes, all placed on
the correct parts from a single front image. But against the anchor it is obviously a
different animal: **no coat**. The Pufferball's fur is a particle system, glTF has no
such concept, so the GLB is the bare body and TRELLIS painted a bald ball. The eyes come
back flat and painted rather than as glossy spheres.

One thing the montage settles that the score could not: the odd read of the side view —
an eye sitting as a disc on the side of the head — is present in the SOLID arm too. It
is the Pufferball's own geometry, not a texturing artefact.

### THE ROTATION THAT SCORED PLAUSIBLY

The first completed run produced `front_full −0.1705` and a "1 of 2 views" verdict.
That result was **wrong and has been discarded**. `preprocess_mesh` normalises to a unit
cube and swaps (y,z) → (−z,y); I reversed that on the way out — but `postprocess_mesh`
already swaps it back (`:369`, "Swap Y and Z axes, invert Y (common conversion for GLB
compatibility)"), so my inverse applied a second rotation and the textured creature came
out 90° about X, on its back.

Nothing complained. The GLB loaded, trimesh was happy, the renderer framed it, the
montage rendered, and DINOv2 returned 0.4367 — a plausible-looking number. It was caught
only by comparing the output's bounding box with the input's: `out_extent_m`
`[0.634, 0.661, 0.541]` against `src_extent_m` `[0.634, 0.541, 0.661]`. That comparison
is now an **assertion that aborts the run**, not a field in the report, because a report
field is only read by someone who is already suspicious.

### Three licence blockers, in order, none of them optional

1. **nvdiffrast** — non-commercial, banned, imported at module scope. Shimmed (§6).
2. **`briaai/RMBG-2.0`** — the background remover named in `texturing_pipeline.json`,
   instantiated inside `from_pretrained` so it blocks CONSTRUCTION. `GatedRepoError:
   401 … Access to model briaai/RMBG-2.0 is restricted`. Its terms are non-commercial
   without a Bria licence, so obtaining the gate token would have moved the problem from
   a crash to a licence breach. Substituted with `ZhengPeng7/BiRefNet` (MIT), the
   BiRefNet class's own default, already in this box's HF cache.
3. Two ordinary bugs behind those: `pipeline.cuda()` half-casts the matting model while
   its stock `__call__` feeds it float32 (`RuntimeError: Input type (float) and bias type
   (c10::Half)`), and `ATTN_BACKEND` must be `xformers` — the config validates against a
   literal list, so my typo `flash-attn` was silently ignored and left the uninstalled
   `flash_attn` default in place, dying ~30 transformer blocks in with 16 GB of weights
   already resident.

**So: the texturing stage does not need nvdiffrast to compute anything, but it cannot be
imported without it, and it cannot be constructed without a gated non-commercial matting
model.** Anyone who later "installs the missing dependencies" to make this work will have
put two non-commercial models into a monetised render path.

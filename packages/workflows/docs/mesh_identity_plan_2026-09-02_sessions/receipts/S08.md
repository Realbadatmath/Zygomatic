## 1. Worker — `/home/zygomatic/models/sam3/sam3d_body_worker.py`

90 lines → 215. Backup at `sam3d_body_worker.py.bak-S08-20260902`. Four changes:

**1. The estimator was being handed BGR as RGB.** `process_one_image` only converts
colour when it is given a PATH; hand it an ndarray and it prints *"please make sure the
input image is in RGB format"*, sets `image_format='rgb'` and skips the conversion
(`sam_3d_body_estimator.py:100-134`). The old worker passed `cv2.imread(path)` — BGR.
**Every single-image fit this box has ever produced ran on channel-swapped input.** The
worker now passes the path. This is the only change that alters what the model *sees*.

**2. Kept fields.** `pred_keypoints_2d` (70×2), `pred_vertices` (18439×3),
`expr_params` (72), `pred_joint_coords` (127×3), `pred_global_rots` (127×3×3) and the
mask were all produced by the estimator and all dropped by the old `keep` tuple. Kept.

**3. Big arrays go to disk.** With `arrays_dir` set, vertices / joint coords / joint
rotations go out as `.npy` and the mask as `.png`; the JSON carries paths. `faces.npy`
(36874×3) is written once. A 112-frame clip's vertices are ~25 MB and have no business
inside a JSON document.

**4. `bboxes` and `masks` per image.** The estimator always accepted them; the request
had no field, so every fit was whole-image single-person. This is what makes the second
person in a two-hander addressable at all.

## 2. MHR decode — `pip install mhr` succeeded, and it still cannot decode

`mhr` 1.0.1 installed into `body_venv` with `--no-deps`. Apache-2.0, read at file level
in the installed wheel (`mhr-1.0.1.dist-info/licenses/LICENSE`, full 202-line Apache
text; README line 219 states it). `--no-deps` deliberately: its `trimesh<5` pin would
downgrade the `trimesh 5.0.0` that SAM 3D Body itself uses, and trimesh is only needed
for the package's optional **mhr↔SMPL conversion tool**, which must never be called
here.

**But `mhr.mhr.MHR` imports `pymomentum`, and that is not installable on this box.**
Meta ships pymomentum through conda/pixi only. The PyPI project literally named
`pymomentum` is **pyMomentum 0.1.4 by Momentum Teknoloji AS — an SMS-gateway client
library** (modules `pyMomentum.sms.providers.mutlucell`, `sanalsantral`). I downloaded
the sdist and read `PKG-INFO` before installing anything. `pymomentum-gpu`, which the
brief named, does not exist on PyPI at all (`pip index versions`: *No matching
distribution found*). Nothing was installed.

Registered in `data/runtime/model_licences_pending/S08.json`: `mhr` as an approved
weight-adjacent entry, `pymomentum (PyPI)` as **REJECTED — wrong package, name
collision**.

Consequence, stated everywhere it matters (module header, `track.json`,
`sam3d_body_service.mhr_decode_available()`): the shape lock is **recorded and
measured, never applied**, and downstream geometry uses the estimator's own per-frame
`pred_vertices`, which needs no decoder. `track.json` carries
`shape_lock_applied: false`.

## 3. `geom/pose_track.py` (970 lines) — the track

`python -m geom.pose_track <clip> --out <dir> [--subject "phrase"] [--fps 17]
[--smooth savgol|oneeuro|none] [--gate] [--soma-probe]`

Runs from **either** venv — verified importable in `body_venv` — because both model
stacks are subprocesses. Chain: ffmpeg at the render fps → SAM 3 phrase-prompted box +
mask per frame, one worker invocation → SAM 3D Body per frame with those boxes → shape
median → temporal filter → `track.json` + `track_arrays.npz` + `masks/m_%05d.png`.

Supporting decisions worth naming:

- **The box track is chosen by IoU continuity, not per-frame score.** Per-frame max
  score is how a two-hander swaps subjects mid-clip. Measured `low_overlap_steps: 0`.
- **`ZYG_SAM3_TIMEOUT_S` is sized to the clip before `sam3_service` is imported.** That
  module reads its subprocess timeout once at import and defaults to 300 s — sized for
  the 8-frame prop-persistence probe it was written for. A whole clip exceeds it, and
  the failure is silent: worker killed, `None` returned, track degrades to whole-image
  without saying so. `sam3_service.py` is not this session's to edit; the env var is
  its documented knob.
- **One GPU lock across both models**, taken with `fcntl.flock` on
  `/home/zygomatic/.zyg_gpu.lock` and held for the whole track, with the inner
  `sam3d_body_service` told to skip its own `flock` (nesting `flock -c` on a held file
  deadlocks). Heavily exercised: with all ten sessions running, six were queued on that
  lock at once and the tracks waited 452 s, 604 s, and once past the full 7200 s
  timeout without ever racing another job.
- **The lock wait BLOCKS; it does not poll**, and that had to be fixed after it bit.
  The first version tried `LOCK_NB` every two seconds. Every other job on this box waits
  with `flock -w 7200 … -c …`, which blocks in the kernel and is woken the instant the
  lock frees — so the poll loop lost essentially every race and one run starved through
  its entire 7200 s budget while `flock -c` waiters behind it took the lock repeatedly.
  It now blocks in the same syscall they do and uses `SIGALRM` for the deadline. **Any
  other session that waits on this lock from python should do the same.**
- **Projection self-check.** The plate rasteriser needs the estimator's camera. It is
  `u = f·(X+tx)/(Z+tz) + W/2`, `v = f·(Y+ty)/(Z+tz) + H/2` with `f = hypot(W,H)`
  (`prepare_batch.py:67-75`, `camera_head.py:60-107`). Verified against the estimator's
  own `pred_keypoints_2d`: **max residual 0.0001 px**. It is the projection, not an
  approximation of it.

### THE DEFECT THIS SESSION FOUND IN ITS OWN TRACK

First run, gated against MediaPipe (§4): **the track lost to its own two-pose-lerp
null — 29.06 px against 23.18 px.** Per the brief, *a track that does not beat the lerp
is not a track*. Diagnosis rather than a retune:

- track beat the lerp on **54 of 79** frames (median 11.42 px vs 18.50 px);
- the mean was destroyed by two contiguous bursts, frames 33-42 and 56-58;
- those bursts contain **exactly the 5 frames whose bbox was `[0,0,832,480]`** — the
  whole image. SAM 3 dropped the subject on 5 of 79 frames, so SAM 3D Body fell back to
  whole-image single-person and **fitted the other man**. Confirmed by eye on an
  overlay: on frames 39 and 57 the track keypoints sit ~60-80 px left of the subject
  while MediaPipe is on him;
- the neighbours of those 5 frames are in the burst because the Savitzky-Golay window
  spread the bad frames' error into them;
- excluding the 8 worst frames: track **20.01** px vs lerp **21.69** px.

**Fixes landed (both are the same principle — a one-frame detector dropout is not the
subject leaving the shot):**

1. `subject_track` now **holds the last known box** across a SAM 3 dropout and flags it
   (`frames[].box_source` ∈ `sam3` | `held` | `none`; counts in `subject_track` and
   `fitted_box_held`). A frame with no box at all keeps `boxed: false` and the track
   says in plain words that it may be a different person's measurement.
2. The **mask sequence holds too**. `m_%05d.png` is indexed positionally by every
   consumer, so one missing number silently shifts every later mask onto the wrong
   frame. `masks_contiguous` is now reported.

### Ledger — four states, per frame, never a silent zero
`found` / `not_found` / `not_detectable` / `unmeasurable`. Both runs: **79 / 0 / 0 / 0**.
The difference is inside `found`: first run had 5 frames with `boxed: false`; final run
has **0 unboxed, 5 `box_source: held`**, and `masks_written: 79`, `masks_held: 5`,
`masks_contiguous: true` (first run wrote 74 masks for 79 frames — the hole the mask
hold closes).

## 4. Gate — per-frame 2D against MediaPipe

`gate_against_2d()`, written to `gate_2d.json`. Reference: MediaPipe BlazePose full via
`geom.keypoints`, visibility ≥ 0.5, on the 19 joints shared between MHR70 and BlazePose
(`MHR70_TO_POSE`). MediaPipe runs **once per frame** and the same detections score the
track and both nulls, so the three cannot disagree about which joints were visible.

Two things the gate had to work around:

- **MediaPipe returns ONE person and this clip has two.** Scored whole-frame it can lock
  onto the other man and the gate would be measuring the distance between two different
  people. Everything outside the track's own box is blacked out first.
- **Blacked out on a full-size canvas, not cropped.** Handing `geom.keypoints.detect` a
  small *portrait* crop on which it does find a body **aborts the process** inside
  MediaPipe's C++ — `image_frame.cc:362 Check failed: 1 == ChannelSize() (1 vs. 4)`,
  reached through `MpImageDataFloat32` when the segmentation mask is read (the
  PoseLandmarker is built with `output_segmentation_masks=True`,
  `geom/keypoints.py:72`). It is an abort, not a Python exception: no `try/except`
  catches it and the gate dies mid-run with no result. Keeping the source frame's
  dimensions avoids it and needs no coordinate offset. **Open item for whoever next
  owns `geom/keypoints.py` — nobody owns it this round, so it was not edited.**

Result, 79/79 frames measured in both runs:

| | first run (px) | **final (px)** |
|---|---|---|
| track, mean | 29.06 | **10.81** |
| track, median | 11.42 | 10.83 |
| track, p90 | 84.75 | **12.06** |
| null: held first frame | 30.48 | 30.43 |
| null: two-pose lerp | 23.18 | 23.10 |
| beats held null | yes | yes |
| beats lerp null | **NO** | **yes** |

**First run: FAILED.** Beat the held null, lost to the lerp — by the brief's rule, not a
track. **Final: PASSES both**, at 1.13 % of the image diagonal. The two nulls barely
moved between runs, which is the point: the nulls are the same clip's endpoints either
way, so the 29.06 → 10.81 improvement is the track getting fixed, not the bar moving.
The p90 collapsing from 84.75 to 12.06 px is the shape of the fix — the distribution has
no tail left, because the tail *was* the five frames fitted on the other man.

MediaPipe is a reference, not ground truth: it has its own error and the joint
conventions differ, so the number that matters is track-vs-nulls measured the same way,
not the absolute value.

## 5. `geom/track_plates.py` (326 lines) — the control plates

`python -m geom.track_plates <track_dir> [--modes ...] [--size WxH]`
→ `<track_dir>/plates_<mode>/ctrl_%05d.png`, the folder S01 passes as `control_dir=`
and S05's picker lists. Five modes, all from `track.json` + `track_arrays.npz`:

- **depth** — painter's algorithm over the 18439-vertex mesh, near = white, same
  convention as `anny_animate.render_depth`. **One deliberate difference:** anny_animate
  normalises over the 2nd-98th percentile of *all* vertex depths, front and back
  together; for a body facing camera that is most of a metre of range of which only the
  near ~15 cm is ever visible, so the plate comes out near-flat and the depth gradient —
  the whole signal a video model reads off a depth control — is compressed. The range
  here is taken over **front-facing faces only**.
- **normal** — camera-space face normals, `(n+1)/2`, same depth ordering.
- **skeleton** — the 18 bones of `char_vace._BONES` in its OpenPose colour order, from
  the track's own 2D keypoints (not a re-detection), so a plate from this module and one
  from `char_vace` are the same modality.
- **seg** — the tracked subject's mask.
- **composite** — depth base with the skeleton over it.

Non-uniform rescale is refused rather than sheared: a plate size whose aspect ratio
differs from the tracked size raises, because the projection is defined in the source
frame.

### Grey-fraction audit (via `vace_control.build` / `audit`, 79 frames each)

|---|---|---|
| depth | 0.1405 % | geometry |
| normal | 0.0000 % | geometry |
| skeleton | 0.0000 % | geometry |

All five pass `audit.ok` (threshold < 5 %). 28.7 s for all five modes × 79 frames

Contact strip written to `plates_composite_strip.png` and checked by eye: the mesh sits

`plates_report.json` carries the per-mode numbers. `main()` exits non-zero if any
requested mode came out constant — the audit is the point, because a flat-grey control
directory looks completely normal on disk.

## 6. Anny mapping (stretch) — MEASURED, AND BLOCKED FOR A NAMEABLE REASON

`soma_registration_probe()` in `geom/pose_track.py`, CLI `--soma-probe`, written to
`soma_registration.json`.

SOMA-X (NVIDIA, Apache-2.0) ships an 18,056-vertex **shared wrap** fitted to each
backend, so wrap vertex *i* on the Anny side and on the MHR side are the same
anatomical point. That shared index is the only Anny↔MHR registration on this box.
Anny is in metres, MHR in centimetres; both y-up.

| measurement | mean | p95 |
|---|---|---|
| similarity fit solved FROM the shared index (s = 0.8961) | **48.7 mm** | 98.9 |
| null: same fit, correspondence guessed by nearest neighbour | 564.2 mm | 1106.9 |
| null: centroid + height scale only, no rotation solved | 57.0 mm | 118.1 |
| Anny vertex transferred through the wrap | 46.7 mm | 96.3 |
| *(not a competitor)* nearest MHR surface point | 26.2 mm | 78.8 |

Reading: **the shared wrap is a real correspondence** — guessing it costs 12× — but it
buys little over a plain height scale (48.7 vs 57.0 mm), because the residual is
dominated by the genuine shape gap between Anny neutral and MHR neutral, not by
registration error. The 26.2 mm figure is reported so nobody later quotes it as the wrap
being beaten: it is a distance to a *surface*, not a correspondence, and it does not
preserve which part of the body a point belongs to.

**The rotation retarget the brief asks for is blocked, and not on effort.** MHR's 127
joints are **anonymous on this box**: `sam3d_body_weights/assets/mhr_model.pt` is a
TorchScript module with no name table (`torch.jit.load`; only `named_buffers` /
`named_modules`), and the joint names live in the momentum character definition that
only `pymomentum` carries — the package that cannot be installed (§2). A joint-NAME
table from MHR to Anny's 163 MakeHuman bones cannot be written from what is on disk. So
the retarget error in joint-position mm was **not measured**. What is available without
names, and is delivered: the vertex correspondence above, and the 19 named `mhr70`
keypoints in `MHR70_TO_POSE`.

Renders depth/normal/matte plates for a **registered** body at front (az 0),
three-quarter (az 45) and side (az 90), on `geom/mv_render`'s turntable

## What the render produced

    [plates] abel: 3 views -> output/body_plates/abel
      front  depth=found  matte=found  normal=found  pose=unavailable
      q45    depth=found  matte=found  normal=found  pose=unavailable
      side   depth=found  matte=found  normal=found  pose=unavailable

So the Blender leg works end to end and the pose channel declares itself exactly
as designed. But the plates themselves are wrong, in two ways neither the exit
code nor the ledger could see.

## Defect 1 — the body was rendered LYING DOWN

`mesh_skeletons` exports the cage **Z-up** into a glTF, and glTF is Y-up by
definition, so Blender's importer applies its Y-up→Z-up rotation to a file that
never needed one.

    registry params.measured.height_m      1.52
    GLB POSITION accessor extent, file Z   1.5200      <- the stature
    GLB POSITION accessor extent, file Y   0.3922      <- the thickness
    manifest height_m from the render      0.3922      <- what it framed on

Every camera was therefore aimed along the body's length: "front" was a view down
the top of the head. Nothing in the ledger could catch this — three views
rendered, three mattes were non-empty, coverage looked plausible at 0.44/0.33/0.30.

**Fix**: after import, compare the vertical and depth extents against the
stature the registry already records and rotate +90° about X only when the
vertical extent misses it *and* the depth extent hits it. Decided by measurement
against a number that already exists, never by "which axis looks tallest".
Recorded in the manifest as `up_fix` and `stature_recorded_m`.

## Defect 2 — the normals were not camera-space

`conditioning.normal_map` computes `n @ r`, i.e. `n_cam[i] = n_world · r[:, i]`,
so `r` must carry the camera basis in its **columns**. Iterating a Blender
`Matrix` yields **rows**, so serialising `cam.matrix_world.to_3x3().transposed()`
was one transpose too many.

Measured against `mesh_control`'s own pufferball plates, which are known good:

    reference front_full   mean RGB [118.8 121.1 214.7]
    reference side_left    mean RGB [143.0 135.2 217.6]
    mine (pre-fix) front   mean RGB [127.0 161.2  30.7]
    mine (pre-fix) side    mean RGB [131.8 225.3 125.5]

The camera-facing channel collapsed from ~215 to 31 and swung 95 points between
views — precisely the world-space signature `normal_map`'s own docstring records
from the Pufferball sheet. A normal ControlNet reads that as a uniformly steep
surface whose tilt flips as the subject turns.

**Fix**: serialise the rotation untransposed.

## The up-axis fix was wrong the first time

`up_fix` reported "rotated +90 about X" while `height_m` stayed 0.3922 and the
three coverage figures came back **byte-identical** to the unrotated render. The
rotation never reached the geometry: Blender's glTF importer expresses its
Y-up→Z-up conversion **as** `rotation_euler = (90,0,0)` on the imported object,
so assigning that same value is a no-op.

Fixed by pre-multiplying `matrix_world` by `Rx(-90)` — a DELTA, correct whatever
the importer chose to do — and the Blender script now **raises** if the
re-measured vertical extent still misses the recorded stature. The original flaw
was trusting an assignment instead of measuring its result, which is the same
mistake in miniature that the whole plan is about.

The clearest evidence of the original defect, for the record:

    PRE-FIX   front bbox 640x412 px of 640   h/w 0.64   <- wider than tall,
    PRE-FIX   side  bbox 640x493 px of 640   h/w 0.77      clipped to full frame width
    FIXED     front bbox 224x348 px of 640   h/w 1.54   <- an upright figure
    FIXED     side  bbox  97x359 px of 640   h/w 3.70   <- a thin profile

## Defect 3 — `fill` under-delivered by exactly 24/36

Found in the same check: `fill=0.82` measured 0.55. Blender's
`sensor_fit='AUTO'` makes the LARGER render dimension use `sensor_width` (36),
so on a square frame the vertical FOV was governed by 36 while the distance
formula divided by `sensor_height` (24). Pinned `sensor_fit='VERTICAL'`; all four
bodies now measure **82%** of frame height against a requested 0.82. A dial that
silently under-delivers is the same class of problem as an inert one.
